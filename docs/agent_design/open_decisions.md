# 미결정 사항

질문·Agent 설계 과정에서 확인되었으나 팀 합의가 필요한 항목입니다. 본 문서의 권고안은 팀원 2의
의견이며 **확정안이 아닙니다**. 최종 결정 상태 열이 `미정`인 항목은 구현 근거로 사용하지 않습니다.

중요도는 현재 MVP 성공 여부에 미치는 영향을 기준으로 구분했습니다. 사소한 구현 세부는 포함하지
않습니다. `DC` 항목은 `docs/data_contracts.md` Draft와 Agent 설계 요구 사이의 차이를 추적하기
위한 별도 목록입니다.

## BLOCKER

### D1. 거래소공시 Parser의 MVP 포함 여부

- **왜 결정이 필요한가** — 18문항 중 6문항이 거래소공시에 의존합니다. 또한 `docs/mvp_scope.md`의
  포함 예정 항목 중 공급계약 정정 추적과 신규시설투자 변경 추적 두 가지가 이 문서군을 전제로
  합니다. 포함하지 않기로 하면 질문 유형 5가 통째로 성립하지 않고 MVP 범위 문서를 함께 조정해야
  합니다.
- **영향 받는 문항** — Q02, Q06, Q12, Q13, Q14, Q15
- **영향 받는 모듈** — `src/disclosure_agent/event` 전체, `retrieval/metadata_filter`
- **현재 상태** — 거래소공시의 구조 분석과 Parser 설계는 **팀원 1에게 별도로 요청된 상태**입니다.
  본 문서는 그 결과를 기다리지 않으며, 설계 방법을 제안하지도 않습니다.
- **권고안** — 팀원 1의 분석 결과가 나온 뒤 MVP 범위·일정과 함께 판단할 것을 제안합니다. 범위와
  일정의 최종 판단은 팀원 3의 관리 범위입니다. 그때까지 해당 6문항은 `Event Parser Pending`으로
  유지하고 삭제하거나 교체하지 않습니다.
- **최종 결정 상태** — 미정

### D2. 단위 정규화의 책임 위치와 시점

- **왜 결정이 필요한가** — 같은 업종·같은 기간·같은 지표인데 기업마다 금액 단위 표기가 다른 사례가
  실제 데이터 사전 검토에서 관찰되었습니다. 정규화를 누락하면 비교 결과에 자릿수 오답이 조용히
  발생합니다. 그런데 현재 문서 사이에 책임 소재가 어긋나 있습니다. `AGENTS.md`는 Parser가 원문의
  값·단위·계층 구조를 보존하도록 정하고 있고, `src/disclosure_agent/periodic/extractor.py`의 예정
  작업에는 단위 정규화가 포함되어 있습니다.
- **영향 받는 문항** — Q07, Q08, Q10, Q12 (직접), Q03, Q04 (숫자 표기 정규화)
- **관련 모듈** — `periodic/parser`, `periodic/extractor`, `agent/calculator`, `common/schemas`
- **결정할 내용**
  1. 정규화를 어느 단계에서 수행하는가 — 원문 보존(Parser) → 정규화(Extractor 또는 Normalizer)
     → 계산(Calculator) 중 어디인가
  2. 원문 값과 정규화 값을 **둘 다 보존**할 것인가
- **권고안** — Parser는 원문을 보존하고 정규화는 별도 단계에서 수행하며, 원문 값과 정규화 값을 모두
  보존할 것을 권고합니다. 근거는 두 가지입니다. `AGENTS.md`의 원문 보존 원칙과 충돌하지 않고,
  사용자가 답변의 수치를 원문과 대조해 검증할 수 있어야 하기 때문입니다.
- **최종 결정 상태** — 미정

### D3. `accounting_scope`의 표현 위치

- **왜 결정이 필요한가** — 사업보고서의 요약재무정보 Section 안에 연결 기준 표와 별도 기준 표가
  연달아 배치되고 행 이름이 동일한 사례가 관찰되었습니다. 연결·별도 구분을 Section 단위 정보로만
  표현하면 같은 Section 안의 두 표를 구별할 수 없어, 요청한 기준과 다른 값을 반환해도 감지되지
  않습니다.
- **영향 받는 문항** — Q01, Q07, Q08, Q10, Q11
- **관련 모듈** — `common/schemas`, `periodic/parser`, `periodic/extractor`,
  `retrieval/metadata_filter`
- **현재 상태** — `docs/data_contracts.md` Draft에 해당 필드가 없습니다. 위 관찰은 **Parser·구조
  분석 결과와 교차 확인이 필요**합니다.
- **권고안** — Section 단위가 아니라 **표 단위로 구분 가능한 형태**를 검토할 것을 제안합니다. 다만
  `docs/data_contracts.md`는 팀 합의 후 확정하는 Draft이므로 **본 설계 작업에서 수정하지
  않았습니다**. `CONTRIBUTING.md`의 Data Contract 변경 절차를 따라 별도로 논의해야 합니다.
- **최종 결정 상태** — 미정

## IMPORTANT

### D4. 시계열 질문의 근거 문서 요건

- **왜 결정이 필요한가** — 사업보고서의 요약재무정보 표가 당기와 전기를 함께 담고 있는 것으로
  관찰되어, 두 기간을 비교하는 질문이 문서 한 건만으로도 답이 나옵니다. 근거 문서를 몇 건 요구할지
  정하지 않으면 정답 기준이 흔들리고, 여러 문서를 검색하는 능력을 평가할 수 없습니다.
- **영향 받는 문항** — Q07, Q08, Q09. 유형 3 전체의 성격
- **관련 모듈** — `retrieval/service`, `agent/evidence`, 평가 데이터셋 구조
- **선택지**
  1. 각 기간의 원 보고서를 각각 근거로 요구한다
  2. 단일 문서 안의 비교 열을 사용하는 것을 허용하고, 시계열 질문을 계산 검증 중심으로 재정의한다
- **권고안** — 1안을 권고합니다. 여러 문서 검색은 18문항에서 유형 3과 유형 4만 검증하는 능력이며,
  2안을 택하면 유형 3에서 그 능력이 빠집니다. 다만 이 결정은 평가 정답 구조에 직접 영향을 주므로
  팀원 3과 함께 확정해야 합니다.
- **현재 문서 반영 상태** — [evidence_and_answerability.md](evidence_and_answerability.md)의
  유형별 최소 요건 표에 **Recommended 값으로만** 기재했고 최종 요건은 Pending으로 표시했습니다.
  [agent_patterns.md](agent_patterns.md)의 Pattern C도 같은 표기를 따릅니다.
- **최종 결정 상태** — 미정

### D5. 정정공시 판본 선택 정책

- **왜 결정이 필요한가** — 정기공시와 거래소공시 모두 정정본이 함께 수집되어 있고, 한 대상에 정정본이
  여러 건 존재하는 경우가 있습니다. 원본을 볼지 최신 정정본을 볼지 정하지 않으면 같은 질문에 대한
  정답이 달라집니다.
- **영향 받는 문항** — Q01, Q05, Q06, Q07, Q08, Q10, Q11. 집계 대상 확정 측면에서 Q12
- **관련 모듈** — `retrieval/metadata_filter`, `event/linker`, 평가 데이터셋 구조
- **권고안** — 정기공시 조회의 기본값을 최신 판본으로 두는 방향을 제안합니다. 거래소공시 단건 요약
  (Q06)에서 원공시를 기준으로 할지 최신 정정 내용을 반영할지는 **별도 판단이 필요**하며 이 문서에서
  확정하지 않습니다. [query_plan.md](query_plan.md)의 `chain_policy` 필드가 이 정책을 표현하는
  자리입니다.
- **최종 결정 상태** — 미정

### D5-a. 기간 미지정 질문의 기본 문서 선택 정책

D5의 하위 항목입니다.

- **왜 결정이 필요한가** — Q05처럼 기간이 명시되지 않은 질문에서 어떤 문서를 기본값으로 선택할지
  정하지 않으면, 같은 질문에 대해 실행마다 다른 문서가 선택될 수 있습니다.
- **영향 받는 문항** — Q05 (직접), 기간이 생략된 모든 질문 (일반)
- **관련 모듈** — `retrieval/metadata_filter`, `agent/query_analyzer`
- **권고안** — 최신 사업보고서를 기본값으로 두는 방향을 제안합니다. **현재는 제안일 뿐이며 확정
  정책이 아닙니다.** 사용자에게 기간 확인을 요청하는 방식도 선택지에 포함됩니다.
- **최종 결정 상태** — 미정

### D6. 평가 데이터셋·대표 질문의 실제 정보 취급 범위

- **왜 결정이 필요한가** — `AGENTS.md`와 `CONTRIBUTING.md`는 실제 접수번호와 실제 기업 수치를
  커밋하지 않도록 정하고 있습니다. 그런데 평가용 정답 문서는 실제 문서를 가리켜야 하고 정답 값은
  실제 수치여야 평가가 성립합니다. 두 요구가 정면으로 충돌합니다.
- **영향 받는 문항** — 전 문항
- **관련 모듈** — `evaluation/questions.jsonl`, `evaluation/gold_answers.jsonl`,
  `docs/evaluation/`, 본 디렉터리의 설계 문서
- **결정할 내용**
  1. 평가 데이터셋에서 실제 문서를 어떻게 가리킬 것인가 — 익명 식별자와 로컬 매핑 표 / 규칙 예외
     명문화 / 평가 데이터셋의 Git 제외 중 선택
  2. **대표 질문에 실제 기업명·연도·계약상대방·사업명을 사용할 수 있는 범위** — 현재 대표 질문은
     실제 데이터 기반으로 설계된 핵심 산출물이므로 임의로 익명화하지 않았습니다. 다만 이 조합이
     특정 공시를 식별할 수 있다는 점은 **저장소 데이터 보안 정책과 함께 팀 확인이 필요**합니다.
  3. **지분공시 기반 문항(Q03)의 개인 식별정보 처리** — Gold·Evidence 작성 시 개인 식별정보가
     포함되지 않아야 한다는 점은 분명합니다. Agent 응답 단계의 처리 수준(C15 PII Filtering)은
     팀 정책 확인 대상입니다.
- **권고안** — 팀원 3이 주관해 결정할 사항입니다. 결정 전에는 `evaluation/` 아래 파일을 채울 수
  없습니다. 팀 확인 전까지 **실제 접수번호·실제 금액·원문 전문·개인 식별정보는 계속 금지**합니다.
  본 디렉터리의 설계 문서들도 이 규칙에 따라 작성되었습니다.
- **최종 결정 상태** — 미정

## Data Contract Draft와의 차이

`docs/data_contracts.md`는 팀 합의 후 확정하는 Draft이며 **본 작업에서 수정하지 않았습니다.**
아래는 현재 Agent 설계 요구와 Draft 사이에서 확인된 차이를 추적 가능하게 남긴 것입니다. 모두
`CONTRIBUTING.md`의 Data Contract 변경 절차를 거쳐 논의해야 합니다.

### DC1. Fact 표현에 기업·회계 기준을 어떻게 담을 것인가

- **Agent 설계 요구** — 기업 간 비교(Q10~Q12)와 연결·별도 구분(Q01, Q07, Q08, Q10, Q11)을 위해
  Fact 수준에서 `company`와 `accounting_scope`를 식별할 수 있어야 합니다.
- **Draft 현황** — Draft의 `Fact`에는 두 항목에 대응하는 직접 필드가 없습니다.
- **Pending** — 어느 계층에서 표현할지 미정입니다. Fact 자체에 둘지, 문서 메타데이터에서 유도할지,
  표 수준 정보로 둘지가 선택지입니다. D3과 함께 논의합니다.

### DC2. Evidence의 문서 내 위치 표현

- **Agent 설계 요구** — 재무 수치의 근거를 지목하려면 Section 경로와 표·행·열 수준의 위치가
  필요할 수 있습니다.
- **Draft 현황** — Draft의 `Evidence`는 Section 식별자와 Chunk 식별자 중심입니다.
- **Pending** — 정합화가 필요합니다. 표·필드 수준 위치를 Evidence에 담을지, 별도 계층에 둘지 미정.

### DC3. 거래소공시의 Evidence 위치 표현

- **Agent 설계 요구** — 거래소공시는 번호가 매겨진 필드 구조로 관찰되어 일반적인 Section 구조를
  전제할 수 없습니다. Q02, Q06, Q12~Q15 여섯 문항의 Evidence가 여기에 해당합니다.
- **Draft 현황** — Draft의 Evidence는 Section·Chunk를 전제합니다.
- **Pending** — 별도의 위치 표현이 필요할 가능성이 있습니다. **Event Parser 결과 확인 후 확정**하며,
  본 문서에서 표현 방식을 제안하지 않습니다.

### DC4. 정정·후속 연결 정보의 표현 방식

- **Agent 설계 요구** — Q13~Q15와 Q12의 집계가 원공시·정정·후속 연결에 의존합니다.
- **관찰 사항** — 원문의 연결 정보가 접수번호가 아니라 날짜와 서류명으로 제공되는 것으로
  관찰되었습니다. **Parser·구조 분석 결과와 교차 확인이 필요합니다.**
- **Draft 현황** — Draft는 이벤트 간 참조를 식별자 참조로 표현합니다.
- **Pending** — 링크 해석 결과와 원문 참조를 각각 어떻게 표현할지 미정입니다. Event Parser 결과를
  기반으로 확정합니다.

### DC5. 용어·어휘 정합

- **Agent 설계 요구** — 본 디렉터리는 지표를 `metric`, 연산 목록을 `operations`로 표기합니다.
- **Draft 현황** — Draft는 Fact의 지표 이름을 `name`으로, 계산 결과의 연산을 단수 `operation`으로
  표기합니다.
- **Pending** — 같은 어휘를 공유할지, 계층별로 다른 이름을 유지할지 미정입니다.

### DC6. 답변 가능성 상태와 사유 코드의 응답 반영

- **Agent 설계 요구** — [evidence_and_answerability.md](evidence_and_answerability.md)가 상태
  3종과 사유 코드 9종을 제안합니다. Q16~Q18은 사유 코드가 서로 달라야 능력이 구분됩니다.
- **Draft 현황** — Draft의 응답 구조에는 경고 목록만 있고 상태·사유 코드 필드가 없습니다.
- **Pending** — 반영 여부와 표현 방식 미정입니다.

### DC7. 검색 단위 모델 정합

- **Agent 설계 요구** — [retrieval_strategy.md](retrieval_strategy.md)는 메타데이터 필터와 구조
  기반 탐색을 우선하고 Chunk 검색을 조건부 fallback으로 둡니다.
- **Draft 현황** — Draft는 Chunk와 검색 결과 Chunk를 검색의 1차 단위로 둡니다.
- **Pending** — 두 모델의 관계 정리가 필요합니다. Chunk 생성 정책이 확정되지 않은 상태와도
  연결됩니다.
